## 2. User Roles and Permission Matrix

The application implements a centralized, deny-by-default access controller ([src/auth/rbac.py](file:///C:/Users/Nandana/.gemini/antigravity-ide/scratch/contractrisk-xai/src/auth/rbac.py)):

| Capability / Resource | `CLIENT` | `LAWYER` (Unverified) | `LAWYER` (Verified) | `SUPERVISING_LAWYER` | `AUDITOR` |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **Register & Manage Own Account** | Yes | Yes | Yes | Yes | Yes |
| **Upload Contracts & View Own Contracts** | Yes (`owner_id`) | No (unless client) | No (unless client) | Yes | No |
| **Access Unassigned Contracts** | No | No | No | Yes (Supervisory) | No |
| **Access Assigned Contracts** | No | No | Yes (`assigned_id`) | Yes | No |
| **View Raw Contract Text / Clauses** | Yes (Own) | No | Yes (Assigned) | Yes | **DENIED (Confidential)** |
| **Perform Lawyer Operations / Approvals** | No | No | Yes | Yes | No |
| **Submit Advocate Credentials** | No | Yes | Yes (Update) | Yes | No |
| **Review / Decide Advocate Verifications** | No | No | No | Yes | No |
| **Self-Verify Own Bar Credentials** | **DENIED** | **DENIED** | **DENIED** | **DENIED** | **DENIED** |
| **Inspect System Audit Logs** | No | No | No | Yes | Yes (Metadata Only) |

## 3. Password Security Implementation

* **Hashing Algorithm**: Argon2id via `argon2-cffi`, strictly adhering to OWASP cryptographic guidelines.
* **Algorithm Parameters**:
  * Memory cost: $65,536\text{ KB}$ ($64\text{ MB}$)
  * Time cost (iterations): $3$
  * Parallelism: $4$ lanes
  * Hash length: $32\text{ bytes}$
  * Salt length: $16\text{ bytes}$ (randomly generated by library per hash)
* **Policy Validation**: Passwords must be between 8 and 128 characters, non-empty, and free of purely whitespace strings.
* **Transparent Parameter Upgrade**: The `needs_rehash` hook checks whether existing hashes match current security parameters upon successful login and updates them automatically.
* **Generic Failure Behavior**: Authentication failures return identical generic errors (`"Invalid email or password."`) whether the account exists or not, eliminating account enumeration vulnerabilities.

## 4. Token & Session Security

1. **Bearer Tokens (JWT)**:
   * Algorithm: `HS256` (HMAC with SHA-256) with algorithm pinning to prevent `none` algorithm attacks.
   * Standard claims: `sub` (User UUID), `email`, `role`, `advocate_status`, `iss` (`contractrisk-xai`), `aud` (`contractrisk-client`), `iat`, `exp` (default 60 minutes), and `jti` (UUID token identifier).
   * Revocation: In-memory/database revocation registry tracks revoked `jti` values upon logout or password reset.
2. **Session Cookies**:
   * Cookie name: `contractrisk_session`
   * `HttpOnly`: Enforced (`True`) to protect against client-side XSS exfiltration.
   * `SameSite`: Configured to `Lax` to prevent Cross-Site Request Forgery (CSRF).
   * `Secure`: Configurable via `CONTRACTRISK_COOKIE_SECURE` (`True` in HTTPS production).

## 5. Advocate Verification State Machine

To uphold professional standards under the Indian legal regulatory framework, lawyer verification enforces a server-side state machine:

```
                  ┌────────────────────────┐
                  │      NOT_APPLICABLE    │ (Default for CLIENT / AUDITOR)
                  └────────────────────────┘
                               │
            (Lawyer submits Bar credentials)
                               ▼
                  ┌────────────────────────┐
                  │  PENDING_VERIFICATION  │◀── Applicant cannot perform lawyer operations
                  └────────────────────────┘
                     │                  │
        (Approved by │                  │ (Rejected by
        Supervisor)  │                  │  Supervisor)
                     ▼                  ▼
        ┌────────────────────────┐  ┌────────────────────────┐
        │        VERIFIED        │  │        REJECTED        │
        └────────────────────────┘  └────────────────────────┘
                     │
         (Revoked / Suspended)
                     ▼
        ┌────────────────────────┐
        │       SUSPENDED        │
        └────────────────────────┘
```

### Verification Requirements:
1. Registration as `LAWYER` mandates `bar_enrolment_id`, `state_bar_council`, and `year_of_enrolment`.
2. Self-verification is strictly prohibited: if `applicant_id == reviewer_id`, the system raises `PermissionError`.
3. Only users possessing the `SUPERVISING_LAWYER` role can review and decide advocate verifications.
4. Every decision requires a formal, recorded decision rationale.
5. All verification state transitions record a tamper-evident audit event (`ADVOCATE_VERIFICATION_SUBMITTED`, `ADVOCATE_VERIFICATION_DECIDED`).

## 6. Contract Authorization & Tenant Isolation Strategy

To support multi-tenancy without breaking existing Task 030 ingestion behavior, `DocumentRecord` incorporates nullable foreign keys:
* `owner_id`: FK $\rightarrow$ `users.id` (Client who submitted the contract).
* `assigned_lawyer_id`: FK $\rightarrow$ `users.id` (Designated panel advocate).

### Enforcement Primitives:
* **Horizontal Isolation**: Client A cannot access Client B's documents (`document.owner_id == user.id`).
* **Lawyer Assignment**: An advocate cannot access arbitrary contracts; access requires explicit assignment AND an active `VERIFIED` advocate status.
* **Auditor Confidentiality Gate**: When an Auditor inspects contracts, the endpoint permits metadata inspection (`require_full_content=False`), but strictly blocks access to the raw contract text snapshots or extracted clauses (`require_full_content=True`).

## 7. Security Audit Trail Integration

The security layer integrates with the existing tamper-evident audit ledger ([src/audit/integrity.py](file:///C:/Users/Nandana/.gemini/antigravity-ide/scratch/contractrisk-xai/src/audit/integrity.py)):
* **Security Event Types Added**:
  * `USER_REGISTERED`
  * `LOGIN_SUCCESS`
  * `LOGIN_FAILED` (records failure reason without logging passwords)
  * `LOGOUT`
  * `ROLE_CHANGED`
  * `ACCOUNT_SUSPENDED`
  * `ADVOCATE_VERIFICATION_SUBMITTED`
  * `ADVOCATE_VERIFICATION_DECIDED`
  * `UNAUTHORIZED_ACCESS_ATTEMPT`
* **Zero Secret Logging**: Plaintext passwords, session secrets, and sensitive credentials are never written to audit payloads or application logs.

## 10. Known Limitations & Boundaries

1. **State Bar Council Registry Integration**: Real-time automated verification via external Bar Council APIs is not available because Indian State Bar Councils do not currently provide public REST APIs for live advocate roll verification. The workflow implements a documented manual verification protocol with a supervising advocate reviewer.
2. **PostgreSQL Row Level Security (RLS)**: While the relational schema and application repository enforce tenant isolation and ownership filtering, database-engine-level PostgreSQL RLS policies require a live PostgreSQL deployment and are not evaluated under SQLite automated tests.
3. **Out-of-Scope Capabilities**: Legal RAG, Indian statutory knowledge base ingestion (Task 032), collaborative review workbench (Task 033), and certified report generation (Task 034) remain strictly locked.
